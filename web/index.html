Envuscator mobile security

Build-specific obfuscation without handing over your secrets.

Envuscator runs inside customer-controlled GitHub Actions and GitLab CI/CD runners. It transforms local configuration into randomized, environment-bound Android and iOS artifacts while keeping source, configuration, binaries, and build logs out of Envuscator infrastructure.

Target outcomes

A narrow control added at the right point in the release path.

Envuscator is intentionally not a secret manager, hosted build farm, or claim that obfuscation makes a mobile application secure. It is an additional layer intended to increase extraction cost, reduce static uniformity, and make builds independently traceable.

Architecture

The service licenses the engine. The runner performs the build.

The architecture separates commercial entitlement from sensitive build execution. Provider adapters authenticate the workload, acquire a bounded download grant, verify an immutable release, and invoke the same local engine contract.

Customer-controlled boundary

What stays in the runner

  • Application source and protected configuration
  • Plaintext temporary material and platform toolchains
  • Generated AARs, XCFrameworks, application binaries, and logs
  • Cleanup, retention, signing, and release policy

Envuscator service boundary

What the service may know

  • Verified provider workload identity and licensed namespace
  • Entitlement state and privacy-minimized audit events
  • Requested engine version and short-lived grant metadata
  • No customer configuration, source, artifacts, or build logs

Security scope

Obfuscation is friction, not confidentiality.

Values embedded in a shipped client can eventually be recovered by a capable adversary. Envuscator does not replace server-side authorization, secret rotation, hardware-backed key storage, platform attestation, runtime integrity, or a secure SDLC. Use it as defense in depth for values that must exist in the client, and keep true secrets off the client entirely.
