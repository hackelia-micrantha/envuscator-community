Micrantha laboratory · mobile security

An extra build-specific security layer for mobile applications.

Envuscator applies randomized, layered obfuscation during your build pipeline to produce a unique protected build for every CI execution. The goal is not impossible client-side secrecy, but a practical increase in the cost of reverse engineering while keeping sensitive build operations inside your own infrastructure.

Engine

Runner-local native generation

Android and iOS generation remain inside the customer-controlled build boundary. Linux/Android engine execution is qualified on repository-scoped rootless JIT; native iOS qualification remains a separate release gate.

Trust chain

Signed release + short-lived entitlement

Release authenticity and workload authorization are separate: adapters verify signed immutable release metadata, acquire a scoped entitlement, retrieve the exact private engine archive, and verify it again before execution.

Explicit limitation

Defense in depth only

No build-time client protection is perfect. Envuscator raises extraction cost but does not turn shipped values into durable secrets or replace backend authorization, attestation, rotation, or runtime security.

V1 architecture · foundation implemented, activation pending

The service licenses the engine. The runner performs the build.

The implemented trust model avoids creating a second sensitive build boundary. Provider adapters authenticate a workload, verify an immutable release, acquire a bounded engine entitlement, retrieve the exact private engine archive from the fixed service authority, and invoke one provider-neutral local engine contract.

  1. 01

    Provider identity

    GitHub OIDC or modern GitLab job identity binds the workload to reviewed provider context. Token-controlled issuer, audience, discovery, and service-origin selection are rejected.

  2. 02

    Entitlement exchange

    The licensing service evaluates normalized grant state and returns a short-lived engine entitlement. Billing-provider identifiers do not enter the signed workload protocol.

  3. 03

    Verified local engine

    The runner verifies signed public release metadata, retrieves the exact entitlement-authorized private archive from the fixed service origin, independently verifies archive identity, and runs locally.

  4. 04

    Artifact and evidence

    The runner receives platform artifacts plus deterministic manifests and normalized evidence while protected configuration, source, private credentials, and build logs remain outside the service.

Customer-controlled boundary

What stays in the runner

  • Application source and protected configuration
  • Plaintext temporary material and platform toolchains
  • Generated artifacts, application binaries, and build logs
  • Cleanup, retention, application signing, and release policy

Envuscator service boundary

What the service may know

  • Verified workload identity and licensed project/namespace scope
  • Privacy-minimized grant, entitlement, and reconciliation state
  • Requested immutable engine identity and short-lived authorization metadata
  • No customer configuration, source, generated artifacts, or build logs

Defense in depth

No client-side protection is perfect.

Given sufficient time and resources, a determined attacker can recover values and behavior from a shipped application. Envuscator does not promise permanent client-side secrecy. It increases reverse-engineering cost by producing build-specific native output and combining complementary obfuscation techniques. It complements, rather than replaces, secure backend authorization, secret rotation, hardware-backed key storage, platform attestation, runtime integrity, and a secure SDLC.

Licensing philosophy

Simple, sustainable licensing without unnecessary lock-in.

The intended pricing model includes a perpetual one-time purchase option alongside recurring plans. Provider-neutral commercial grant and reconciliation foundations are implemented, but checkout, production billing reconciliation, public wrappers, and product tiers are not yet presented as generally available. Paid local/offline licensing is a separate later contract rather than a weaker fallback from CI identity.
