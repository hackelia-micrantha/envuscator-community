Current state

Envuscator is incubating. The provider-neutral contract and customer-runner trust boundary are defined while the production adapters and entitlement service are implemented.

The v1 commercial model is licensed CI delivery, not hosted customer builds. Source code and protected configuration stay on customer-controlled runners.

Intended users: mobile developers, platform teams, and security teams that want another defensive layer without treating obfuscation as a secret-management system.

How it works

One contract across GitHub, GitLab, and local builds.

01

Materialize protected configuration

The CI platform writes a protected configuration file onto the customer runner. Configuration values are not ordinary workflow string inputs.

02

Verify entitlement and engine

The adapter exchanges workload identity for entitlement, resolves an immutable engine version, and verifies its expected identity before use.

03

Emit a bounded native artifact

One Android or iOS build produces an AAR or XCFramework with normalized manifests, checksums, and provenance metadata where available.

Why this matters

  • Raises the cost of static configuration extraction
  • Keeps customer source and build inputs on customer-controlled runners
  • Provides consistent behavior across GitHub, GitLab, and local execution
  • Adds supply-chain verification, manifests, and leak-focused controls

Honest scope

Envuscator is one defense layer. Shipped applications and embedded values must still be treated as inspectable, and secure backends, attestation, rotation, and least privilege remain necessary.
